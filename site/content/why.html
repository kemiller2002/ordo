Why Ordo

The hard part was never writing the code

An agent can produce a plausible implementation of almost anything. What it cannot reliably do is know where the change belongs, what it is allowed to affect, which states are valid, and what would count as finished — because in most codebases nobody wrote those down.

What the industry measured when it checked

The optimistic case is real and narrow. {{ref:R-COPILOT}} found 95 developers completing a bounded, automatically scored, greenfield task 55% faster with assistance. That result holds, for that kind of task.

Then the harder measurements arrived. {{ref:R-METR-RCT}} put sixteen experienced maintainers on 246 real issues in repositories they knew well and found them 19% slower with AI available. The striking part is not the slowdown; it is that they could not perceive it. They forecast 24% faster beforehand and still believed they had been 20% faster afterwards.

At organisational scale, {{ref:R-DORA-2025}} found AI adoption now correlating with higher delivery throughput and higher delivery instability at the same time — more change failures, more rework, longer recovery. The throughput problem got solved. The stability problem did not.

{{ref:R-PRP}} names the shape across more than ten thousand developers: 98% more pull requests, 91% longer review times, flat delivery. Industry analysis has a name for the missing term — a verification tax on code that reads as correct.

Put together: generation is cheap now, and everything downstream of generation is not. Reviewing, verifying, integrating and recovering from AI-written code is where the cost went. DORA's own explanation is that change volume has outrun the control systems meant to absorb it.

Why more tests do not fix it

The obvious response is to test harder. Two independent findings say that does not address this failure class.

{{ref:R-METR-HOLISTIC}} took eighteen real tasks in two mature repositories and found agent solutions that passed the reference tests and still failed merge-readiness review — on testing, documentation, formatting, typing and general quality.

We found the same thing from the other direction. A fresh reviewer examined a build that had already passed a 90-test suite, a strict type check, a dependency audit, an architecture check and an adversarial self-review with mutation testing. It found five defects, and {{metric:M-GF2B-OVERLAP}} had been caught by any of it. In a separate build, the test suite {{metric:M-GF2A-DEFECTS}}.

A test suite checks what its author thought to assert. That is enormously valuable and it is not the same as checking whether the work is right.

The specific failures this produces

Code that compiles, passes, and does nothing

A boundary arm exists, type-checks, satisfies the architecture check and the contract tests — and does no work. We removed one deliberately: {{metric:M-HN1-SILENT}} objected. Five targeted mechanisms were then built to close that class, and re-tested: {{metric:M-HN2-NOOP}} caught it. Only a live integration test did, in every trial.

A rename that changes meaning in silence

When duration stopped meaning six-minute units and started meaning minutes, the compiler caught eight sites and around {{metric:M-TE-CS-SILENT}} more passed the value as a bare positional integer. Identical source text, six times the duration, green build, passing tests. Two came out correct {{metric:M-TE-CS-COINCIDENCE}}.

One fact, several copies, no agreement check

The one value a compiler protected had zero duplication. The two outside its reach were duplicated four times and twice, with nothing checking the copies agreed. A shared type does not fix this: the identical type produced three different wire behaviours depending on the call path, inside one process.

A declared outcome nothing can produce

A reconciliation result declared four outcomes and the code could construct three. Every caller handled a case that would never arrive, and believed it was covered. Ninety tests and a mutation-tested self-review did not find it.

What Ordo does instead

It moves the constraints out of convention, documentation and tribal knowledge, and into structures a machine can act on. State becomes a named thing that is stored rather than inferred. Change happens through declared transitions, so illegal actions are unavailable rather than defended against. A rule has one authority, so the copy that drifts does not exist. Verification is several mechanisms whose blind spots differ, because one mechanism has been measured to be insufficient.

{{ref:R-PRP}} reaches the same conclusion from the outside: under specification governance, the bottleneck on velocity moves from generation to specification clarity. Two independent builds of the same frozen requirements show that clarity is reachable — {{metric:M-GF2A-AC}} traced criterion by criterion, twice, with all nine open questions preserved rather than guessed past.

Where we expected a result and did not get one

Three things this research programme believed, measured, and gave up. They stay published because a methodology that only reports its confirmations is not offering you evidence.

  • That explicit domain types reduce the cost of propagating change. Tested with everything else held constant: no measurable difference on field renames, and no help from either type system on arithmetic business rules. The result →
  • That making boundaries explicit reduces boundary work. It does not. {{metric:M-HN2-BCA}} — measured three times, across two architectures, identically. It changed how the work was found, not how much of it there was.
  • That a higher mechanical discovery rate means lower cost. In one paired trial the hardened condition scored {{metric:M-HN3-MDR}} on discovery while spending less on search and repair. The two proxies moved in opposite directions on the same mission.
