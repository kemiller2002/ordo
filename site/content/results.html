Results

What happened when we measured it

{{count:experiments}} recorded trials across {{count:codebases}} codebases. This page is organised by conclusion, not by chronology, and it includes the trial that refuted the hypothesis it was built to test.

A passing test suite is not evidence the work is done

This is the strongest conclusion on the site, it is supported from two independent directions, and it is the one with the clearest operational consequence.

{{metrics:M-GF2B-OVERLAP,M-GF2B-DEFECTS,M-GF2A-DEFECTS}}

A fresh agent, with no knowledge of how a build had been constructed, reviewed a finished implementation that had already passed a 90-test suite, a strict type check with noUncheckedIndexedAccess and exactOptionalPropertyTypes, a dependency audit, an architecture check, and an adversarial self-review that included three mutation tests deliberately breaking shared guards to confirm they were load-bearing.

It found five defects. None had been caught by any of that. One was a result case declared in a type that no code path could construct — the type checker was satisfied, ninety tests were satisfied, and the contract was incomplete.

Independently, {{ref:R-METR-HOLISTIC}} found the same shape in someone else's repositories: agent solutions passing reference tests and still failing merge-readiness review. Two research programmes, different codebases, same finding.

{{diagram:verification}}

Why this matters operationally. If a green suite is your merge signal, and a green suite does not distinguish merge-ready work from work that merely passes, then raising test counts does not buy you what you think it buys. The fix is not more tests of the kind you have. It is at least one mechanism whose blind spot differs from theirs.

Limit. One verification pass on one codebase. It shows these mechanisms missed what that reviewer found; it does not quantify how much any mechanism generally misses. Every agent involved came from one model family, so a shared blind spot cannot be ruled out.

Conventional code goes quiet exactly where it matters most

The same domain was rebuilt under a deliberately ordinary persona — a competent professional developer reaching for mutable classes and bare primitives by default. Not a strawman, and the distinction matters: the finding is about type design, not carelessness.

{{metrics:M-TE-CS-SILENT,M-TE-CS-COINCIDENCE,M-TE-JS-LANGUAGE}}

When the unit of measure changed, renaming the duration field caught eight call sites in the compiler. Around fourteen more passed duration as a bare positional integer — where the literal 10 had meant ten six-minute units, sixty minutes, and now meant ten minutes. Identical source text, six times the duration, no compile error. The build was clean and all thirty tests passed while that was unresolved.

In the JavaScript rebuild, the language caught nothing at all, at any point, for any reason. A property rename across two production files produced zero errors, zero warnings and zero crashes. The program ran.

Against that, the state-structured builds: every ripple location surfaced {{metric:M-TE-CSSTATE-RIPPLE}}, and in the F# trial {{metric:M-TE-FSSTATE-RIPPLE}} across two root causes — each root cause showing every affected call site at once. Zero required a manual search.

Limit. Comparing the state trials against the conventional rebuilds is partly a comparison of persona, and the state trials' own reports say so. What is not a persona effect is the structural point below.

The difference, stated as numbers

The two tables below are the whole comparison. Everything else on this page is context for them. Every figure links to its own record — definition, how it was measured, what it does not show, and the file and section to check it against.

2. Mistakes, by the mechanism that caught each one

This is where the popular version of the claim breaks. Raw mistake counts do not favour more static checking — the build with the least of it scored best. What differs is which mechanism did the catching.

Two things about this table that we corrected rather than presented cleanly.

The C# mechanism rows sum to seven catch-events over six mistakes, because F7's stale revision was caught twice — first by a pre-build read-through, then by the compiler. The rows do not partition, and are not presented as if they do.

The compiler figure was also published here as 4 of 6 and is now 3 of 6. The source log's tally of four included the eight rename sites from the unit change, which are the compiler propagating an intended change rather than catching a mistake — the log's own row for that requirement records zero mistakes shipped. Those eight are real and belong in table 1, where they now are. They were never a mistake count.

What the two tables together support, and nothing more: the conventional C# rebuild made {{value:M-TE-CS}} mistakes and the JavaScript one {{value:M-TE-JS}}, at comparable size. Of the C# six, {{value:M-TE-CS-SELF}} were invisible to every mechanism and were caught only because someone deliberately re-read a diff before running it. Swapped string arguments, a stale revision inside a loop, a signature change hidden behind var — none of these is catchable by a compiler even in principle. In the state-structured builds the equivalent substitution is unwritable, because a duration and a time are different types. That is the claim. It is a claim about which failures remain possible, not about how many occur.

Why this table has two columns and not four. The two state-system trials did not log mistakes in this format — their records classify defects by class and report {{metric:M-TE-CSSTATE-DEFECTS}} and {{metric:M-TE-FSSTATE-DEFECTS}} runtime domain defects respectively, which is not the same measurement. Rather than convert between formats and present the result as like-for-like, the columns are left absent. Table 1 is the four-way comparison, because propagation was recorded the same way in all four.

Some things are not measured — they are guaranteed

These are properties of the code, verifiable by reading it. They carry no confidence interval because they are not statistical claims.

A duration cannot be passed as a time

TimeOfDay and DurationMinutes are separate nominal types, with the source comment stating the reason: so a caller "cannot pass a duration where a time-of-day is expected and have it compile." The failure mode from the section above is not unlikely here. It is unsayable.

A missing case is a build error

The entry lifecycle is a closed set with exhaustiveness checking elevated to a build error. Adding a state does not risk a forgotten branch; it produces a failing build at every site that must now decide what the new state means.

No half-transitioned value is observable

Every command produces a new immutable value rather than mutating one in place. There is no public setter, so a caller holding a reference from before a command ran sees the pre-transition value — never a partially updated one.

A terminal state is tested, not assumed

Nothing leaves Superseded. Every guard refuses it and two acceptance criteria assert the refusal — so the constraint is verified rather than merely absent from the code, which is indistinguishable from an oversight.

Specification clarity is reachable, and it is the new bottleneck

{{ref:R-PRP}} concludes that under specification governance the constraint on velocity moves from generation to specification clarity. Two independent builds of the same frozen requirements tested whether that clarity is actually achievable by an agent.

{{metrics:M-GF2A-AC,M-GF2B-SCOPE,M-GF2B-CONVERGE}}

Both builds implemented all 12 product requirements, all 20 business rules and all 58 acceptance criteria, with an ID-by-ID mapping from each criterion to the test covering it. Both preserved all nine open questions as unresolved rather than guessing past them. Neither had seen the other's work.

They converged on the same seven entities, the same three state machines, the same transition set, a mathematically identical overlap formula and an identical billing formula — and independently arrived at the same architecture for deriving capabilities from the predicates the transitions enforce, documenting the reason in nearly the same words. Across 41 requirement-level decisions they differed on one, and that one was a scope question about what to build rather than a disagreement about a rule.

Cold-start reconstruction was also tested directly: {{metric:M-TE-CSSTATE-COLDSTART}} — what the application does, where authoritative state lives, which transitions are legal, where each workflow is implemented and how it is tested, all answerable from the generated documents without opening a source file.

Limit. Two builds are a replication, not a sample, and both came from the same model family — convergence between similar systems is weaker evidence than convergence between different ones. The cold-start figure was self-assessed after a documentation gap had been closed, not tested on an actual fresh reader.

Requirements-first construction held up

{{metrics:M-TE-CSSTATE-DEFECTS,M-TE-CSSTATE-REWORK,M-TE-CSSTATE-SEARCH,M-TE-CSSTATE-CONTEXT}}

Recovering the requirements, modelling the states, and only then implementing produced a first pass with no runtime domain defects and nothing rewritten because earlier work was wrong. All sixteen domain files touched contained semantic decisions; none contained only mechanical propagation. Eighteen searches across the entire trial, with no occasion where in-hand context proved insufficient.

Limit, and it is a real one. This was a single uninterrupted pass with no later requirement change to force rework. The trial's own report is explicit that Semantic Change Coverage is therefore not applicable rather than zero, and that a fair claim about reduced rework would need a follow-up change-task trial it did not run. We are not making that claim.

What we tested and did not find

The most tightly controlled experiment in this evidence base was built to test whether explicit domain types reduce the cost of propagating a change. It held feature scope, code quality, the change itself and the agent constant, varying only the presence of opaque types, with falsification criteria set in advance.

It refuted the hypothesis in its stronger form.

{{metrics:M-TE-BASELINE-RENAME,M-TE-BASELINE-ARITH,M-TE-BASELINE-MISSED}}

On field renames, both the conventional and the explicitly-typed implementation caught every call site automatically — no measurable difference. On arithmetic business rules embedded in expressions, neither type system helped: a wrong divisor compiles cleanly in both, because the value is a bare number until it crosses a smart constructor.

The one asymmetry observed was a discovery failure, not a type failure — a pattern search missed a site where the same rounding was written as a division by 360 rather than by 6. And the report traces even that to architecture rather than language: the explicitly-typed domain routed arithmetic through named accessors, so there were fewer raw sites to miss. That discipline is achievable in either language.

The hypothesis record remains open rather than supported. We publish this because an evidence base that only contains its own confirmations is not an evidence base.

What none of this establishes

  • Nothing about cost or schedule. Token and cost telemetry was unavailable for most trials, and the one experiment that produced cost figures for a paired comparison was interrupted mid-run, leaving its treatment condition a documented lower bound rather than a total.
  • Nothing about repeated change. No change-task trial has been run against a state-structured codebase, so the argument that Ordo's advantage compounds across successive changes has no data behind it. It is plausible and it is unmeasured.
  • Nothing about teams. Every trial was executed by a single agent or a single supervised session.
  • Nothing about experts in familiar code. {{ref:R-EXPERTISE-REVERSAL}} predicts that structure which helps a newcomer can add load for someone who already holds the model. Ordo asks for declarations up front; for an expert in a codebase they know well, that is a cost we have not measured.
  • Nothing beyond four languages. F#, TypeScript, C# and JavaScript. No claim about Java, Go, Rust, Python or anything else.
  • No comparison against unconstrained development of the same requirements. None of the trials has a counterfactual arm.
