Concept 5

Boundaries and authority

A boundary is where a value leaves the place that understands it. This is where this research programme found most of its defects, every time it looked.

Two failure shapes

Representation collapse

A closed value becomes open

A named alternative crosses a boundary and arrives as an arbitrary string. The domain permits four things; the boundary admits anything. Nothing fails at the crossing — it fails later, somewhere that cannot tell it was ever constrained.

Uncoordinated duplication

One fact, several copies, no agreement check

The same vocabulary maintained in the domain, in the persistence schema and in the wire format, by hand. Adding a case updates one of them and produces silence at the others.

Experiment 1 measured both in one codebase. The single fact the compiler protects had zero duplication. The two facts outside its reach were duplicated four times and twice, with no automated check that the copies agreed.

What a shared type does not buy you

The intuition that two components in one language sharing one type are therefore safe at their boundary was tested directly, and refuted. The identical shared type produced three different wire behaviours depending on which call path reached it — inside a single process.

A type is a promise about values in memory. It is not a promise about what a serialiser emits. That is a different artifact, and Ordo asks for it to be specified deliberately rather than inherited from whatever a library does by default.

What hardening the boundaries changed

Experiment 2 built five mechanisms against Experiment 1's specific blind spots: a constraint-agreement test between the database and the domain, a single-source wire discriminator, exhaustive dispatch replacing string dispatch, a field-vocabulary agreement test, and a fixture forced to a compile error when a case is missing.

{{metrics:M-HN1-MDR,M-HN2-MDR}}

One of those mechanisms did something better than mechanising discovery. Making the wire discriminator single-sourced removed the site entirely — there was no longer anything there to find. That distinction, between making a change easier to find and making it unnecessary, is worth more than the discovery-rate improvement.

What hardening did not change

{{metrics:M-HN2-BCA,M-HN3-BCA}}

Four boundary files per semantic decision, measured three times, across three domain cases and two architectures, identically. Hardening changed how required boundary work was found. It did not change how much of it there was.

This is recorded permanently as a contradicted proposition (CL-006) so that nobody proposes it again without seeing why it was rejected. If somebody tells you that making boundaries explicit reduces the number of places a change touches, the only measurements here say otherwise.

And one tier nothing guarded at all

In the paired trial, 7 of 19 required sites fell in the HTTP tier, which had zero mechanical guard on either architecture. That is the single biggest reason the hardened condition's discovery rate came in below its own preregistered prediction.

A candidate mechanism for that tier is sketched in the source report. It has not been built and it has not been tested, and this site does not claim it works (CL-009).

What an agent should do differently

  • When adding a case to a closed set, ask where that set is restated — persistence constraints, wire formats, validation lists, test fixtures. Compiler silence at those places is not agreement.
  • Do not treat a shared type as a boundary contract. Specify the wire representation, and check it.
  • Where duplication cannot be removed, add a mechanical agreement check. A comment saying "keep in sync" is not one.
