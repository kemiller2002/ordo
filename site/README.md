# The Ordo website

The public site for Ordo — the methodology this repository develops under the
name State-Directed Engineering. Generated by `src/Ordo.Site`, deployed to
GitHub Pages by `.github/workflows/pages.yml`.

This file is the maintenance contract. Read it before changing anything under
`site/`.

## Why the site is named differently from the repository

`research/decisions/DF-SDE-2026-0005` records the decision: **Ordo** is the
public name, **State-Directed Engineering** is the name in the research record,
and they are the same methodology. Research artifacts are not renamed, because
their names are part of the experimental record and every published number
traces back through them. New public content uses *Ordo*; citations resolve to
SDE-named artifacts, and `/about/` explains the difference to the reader.

## Where authoritative content lives

Nothing under `site/` is semantic authority. It is a presentation of authority
that lives elsewhere:

| What | Authority | Where the site gets it |
|---|---|---|
| Methodology rules | `doctrine/`, `method/` | Restated in prose under `site/content/`, cited back |
| Evidence and metrics | `research/evidence/`, and the experiment repositories | `site/data/evidence.json` |
| Proposition confidence | `doctrine/EVIDENCE-TO-ENGINEERING-MAP.md` | The `claims` array of `site/data/evidence.json` |
| Defined terms | `doctrine/GLOSSARY.md` | The `glossary` array of `site/data/evidence.json` |
| Independent research | External publications | The `references` array of `site/data/evidence.json` |

If doctrine changes, the site does not follow automatically. That is a
deliberate gap, not an oversight: an automatic copy would make the site a
second authority whose disagreement with the first nobody would notice. Update
`site/data/evidence.json` in the same change that updates doctrine.

## Layout

```
site/
  data/site.json        site name, description, canonical URL, path prefix, navigation
  data/evidence.json    repositories, experiments, metrics, claims, references, glossary
  data/claim-sources.json  generated internal claim-to-source map (never published)
  content/**.html       authored pages: front matter + semantic HTML fragment
  narratives/<slug>.html  optional interpretation section for one experiment page
  assets/               stylesheet and favicon, copied verbatim to the site root
src/Ordo.Site/          the generator and its validator (F#)
tests/Ordo.Site.Tests/  the test suite
```

## Local development

```sh
dotnet test tests/Ordo.Site.Tests/Ordo.Site.Tests.fsproj   # parser, tokens, validation, determinism
dotnet run --project src/Ordo.Site -- validate --site site # build in memory and check, write nothing
dotnet run --project src/Ordo.Site -- build --site site --out dist
```

`build` validates before writing. If validation fails, nothing is written and
the previous `dist/` is left untouched. `dist/` is not tracked.

To preview, serve `dist/` under the path prefix in `site/data/site.json`, or
set `pathPrefix` to `""` locally and serve `dist/` at a root.

## Adding a page

Create `site/content/<name>.html` beginning with a front-matter block:

```
---
path: /concepts/example/
title: Example
description: One sentence for the meta description and social card.
section: Concepts
order: 40
summary: One sentence, reused in indexes, /data/index.json and llms.txt.
---
<section class="page-intro">…</section>
```

All six keys are required; `path` must start and end with `/`; `order` must be
an integer. A page joins its section's index automatically — `{{section:Concepts}}`
renders the cards — so there is no list of pages to keep in step.

Write semantic HTML. Start the page body with exactly one `<h1>`, never skip a
heading level, and give every image that carries meaning an `alt`. The build
enforces all three.

## Adding evidence

Every number the site publishes is a record in `site/data/evidence.json`. Add
a metric there and reference it from prose with `{{metric:ID}}`; never type a
number directly into a content file.

A metric record requires all of:

```json
{
  "id": "M-EXAMPLE",
  "label": "What it is called",
  "value": "59 / 59",
  "definition": "What exactly this measures.",
  "measurement": "How it was collected, by what instrument.",
  "experiment": "an-experiment-id",
  "provenance": "instrumented | self-reported | derived | not-observable",
  "limitation": "What a reader must NOT conclude from this.",
  "source": { "repository": "a-repository-id", "path": "path/in/that/repo.md",
              "ref": "commit-sha-or-tag", "section": "optional heading" }
}
```

`limitation` and `source` are not optional and there is no way to omit them:
the manifest parser rejects the record, and the build fails. An experiment
record likewise requires at least one entry in `limitations`.

**`value` is rendered exactly as written.** Do not round, reformat, or convert
a range into a single figure. If a value is a lower bound, a partial reading,
or a corrected figure, say so in `limitation` and keep the raw form.

**Use `not-observable` rather than omitting a metric** whose telemetry does not
exist. Missing is not zero, and an experiment that publishes only its available
numbers has published a filtered result without saying so.

## How metrics reach the page

`{{metric:ID}}` renders the value inline as a link to its card on the
experiment page it belongs to. `{{metrics:ID,ID,…}}` renders full cards with
definition, collection method, limitation and citation. Both fail the build if
an id does not exist, which is the whole mechanism: a stale reference cannot be
published, and neither can an invented one.

Other tokens: `{{claims}}`, `{{claims:CL-001,CL-002}}`, `{{experiments}}`,
`{{repositories}}`, `{{glossary}}`, `{{references}}`, `{{ref:R-ID}}`,
`{{count:subject}}`, `{{section:Name}}`,
`{{diagram:transition|engineering|verification|lifecycle}}`, `{{link:/path/}}`.

**Never write a count of anything in this manifest as a literal.** Use
`{{count:experiments}}`, `{{count:codebases}}`, `{{count:metrics}}`,
`{{count:claims}}`, `{{count:repositories}}`, `{{count:references}}`,
`{{count:glossary}}` or `{{count:contradicted}}`, which render the number as a
word up to twenty and a numeral above it. A literal count is a second copy of a
fact the manifest states first, and a copy nothing checks is the defect class
this site exists to describe: the evidence index read "seven experiments" for a
while after the manifest reached eleven, and every mechanism here passed it,
because each half was internally valid and nothing compared them.

Two consequences for authoring. Front matter is not token-expanded, so a
`summary` or `description` must not state a count at all — write around it.
And a count that names a *subset* must be written so it cannot be read as a
total: "three of the experiments", not "three experiments". A test rejects a
statement that opens with a count of experiments disagreeing with the manifest,
and it matches the opening position precisely so that transcribed evidence text
saying "across three experiments" is left alone.

`{{ref:R-ID}}` cites independent, external research inline; `{{references}}`
renders the whole table with each study's finding and its stated limits. These
are deliberately a different type from a metric's `source`: a source points into
a repository this organisation controls, a reference points at work it does not,
and the renderer styles them differently so a reader can tell at a glance which
kind of authority a claim is resting on. An external study needs a `limitation`
for the same reason a metric does — cited without its boundary it is being used
as authority rather than as evidence.

## Editorial posture

The site leads with outcome and mechanism, not with experiment chronology. Two
rules from `kemiller2002/communication-engineering` govern the prose and are
worth restating because they are easy to lose under marketing pressure:

1. **An example is not a warrant.** An analogy or a code sample can make a
   relation imaginable without establishing it. Warrant comes from the evidence
   manifest or from a cited study, never from the vividness of an illustration.
2. **No holding voice.** We do not have adjudicative authority over the
   question of whether Ordo works. Pages use invitation and evidence rather
   than the grammar of a settled verdict.

Page architecture follows the function each page performs: the home page and
`/why/` build a case from familiar ground through objections; `/results/`
narrows a question, concedes its limit, connects the effect and states what
follows; `/adoption/` is task-linear; `/comparison/` is a dimension table.

## Internal claim-source map

`site/data/claim-sources.json` maps every published metric to its artifact,
experiment, provenance class and stated limitation, plus every external
reference. It is **not published** — the generator does not copy `site/data/`
— and it exists so a maintainer or auditor can check any figure without the
public pages carrying a citation on every number. Regenerate it whenever the
manifest changes:

```sh
python3 scripts/claim-sources.py
```
Use `{{link:…}}` for internal links so the deployment path prefix stays in one
place.

## What the build refuses

`Ordo.Site.Validate` runs against the exact bytes that would be published,
before anything is written, and reports every failure from every check in one
run:

- a required page or data file is missing
- an internal link resolves to a file that was not generated
- a link fragment points at an id no page defines — the way citations break
- a page has no title, no meta description, no `lang`, no main landmark, more
  than one `<h1>`, or a skipped heading level
- an unfinished draft marker (`TODO`, `TBD`, `FIXME`, `XXX`, and similar)
  survives into the output
- anything shaped like a credential appears in a published file
- a generated JSON document does not parse

## Deployment

`.github/workflows/pages.yml` runs the test suite, generates the site,
re-checks it, reports the payload size to the job summary, and deploys. Pull
requests build and validate but do not deploy.

The site is served from the custom domain **`ordo.echelonfoundry.com`**,
configured in *Settings → Pages* with *Source: GitHub Actions*. The build
writes a matching `CNAME` into the artifact so the expected domain is visible
in the repository rather than only in a settings page.

**A custom domain serves the site from its root.** `customDomain`, `baseUrl`
and `pathPrefix` in `site/data/site.json` are three statements of one fact, so
the build checks that they agree: with `customDomain` set, `baseUrl` must be
`https://<customDomain>` and `pathPrefix` must be empty. Disagreement fails the
build and reports both halves at once.

This check exists because the first deployment did not have it. The site was
generated for a project-page prefix (`/state-directed-engineering`) and served
from the custom domain's root, so every internal link and the stylesheet
resolved to nothing — and every mechanical check passed, because each field was
internally valid and nothing compared them. If the domain ever changes, change
all three fields together; the build will refuse anything else.

## Visual consistency with Echelon Foundry

`site/assets/css/ordo.css` derives its palette, type stack, spacing, sharp
bordered grids, focus treatment and ambient grid motif from the Echelon Foundry
site (`kemiller2002/consulting-company`, `assets/css/style.css`). Keep them in
family:

- Use the `--ef-*` custom properties. Do not introduce a new colour.
- **Oxide Bronze and Verdigris are prohibited for normal text on Stone or on
  Foundry Charcoal.** That constraint comes from the parent site's own
  colour-contrast test, which asserts those four pairings fail. Use them on
  Parchment, or as borders and rules.
- No rounded corners, no gradients, no shadows. Structure comes from one-pixel
  borders on grids.
- No client-side JavaScript. The site works fully without it, and there is
  currently nothing it would be for.

## What not to change without evidence

- **Do not soften a limitation.** Every `limitation` field and every
  `limitations` entry is load-bearing. Several exist specifically because a
  source record insists the caveat must never be dropped downstream.
- **Do not remove a contradicted claim.** The five `contradicted` rows stay
  permanently so that nobody re-proposes them without seeing why they were
  rejected. That mirrors the rule in `doctrine/EVIDENCE-TO-ENGINEERING-MAP.md`.
- **Do not promote a confidence class** without new supporting evidence and a
  recorded reason, per that same document.
- **Do not add a number that has no artifact.** If you cannot cite it, it does
  not go on the site. This is enforced mechanically, but the enforcement only
  catches the shape — you still have to check that the artifact says what the
  record claims it says.
- **Do not resolve a disagreement between two records by choosing one.**
  Publish the disagreement and investigate whether definitions, populations or
  measurements changed.
