# Ordo Executable Intelligence Requirements — Pass 3

Status: Third-pass consolidation and implementation requirements
Purpose: Convert the first two Ordo executable-intelligence requirement passes into a buildable, prioritized, implementation-ready plan without introducing unnecessary framework scope.

This document supplements Pass 1 and Pass 2. It focuses on consolidation, canonical terminology, release boundaries, implementation sequencing, minimum viable public API, and the first production vertical slice.

If this document conflicts with an earlier requirement, the conflict must be surfaced explicitly. This document does not silently supersede earlier semantic requirements unless stated.

======================================================================
1. PASS 3 OBJECTIVE
======================================================================

### ORDO-3-001 — Pass 3 shall reduce ambiguity
Pass 3 exists to make implementation choices explicit enough that an agent does not need to invent architecture.

### ORDO-3-002 — Pass 3 shall not add speculative platform scope
The purpose of this pass is consolidation and implementation readiness, not feature expansion.

### ORDO-3-003 — Existing Ordo methodology remains authoritative
Executable Ordo remains subordinate to existing Ordo methodology, construction rules, verification rules, navigation rules, structural-locality rules, and research practices.

### ORDO-3-004 — Executable Ordo shall remain small
If a requirement can be satisfied with a small set of discriminated unions, records, functions, and narrow interfaces, do not introduce a larger abstraction.

### ORDO-3-005 — The first implementation must prove value vertically
The first release must demonstrate one complete resolution path from domain state through decision resolution to accepted/rejected/escalated transition and observable execution evidence.

2. CANONICAL TERMINOLOGY
======================================================================

### ORDO-3-010 — ResolutionMode
Canonical values:
- Compute
- Decide
- Deliberate

Do not use SystemOne/SystemTwo/Fast/Slow as public API types.
Those terms may appear in research documentation as conceptual inspiration only.

### ORDO-3-011 — DecisionContract
Represents a bounded semantic question with a legal typed output space.

### ORDO-3-012 — DecisionRequest
Represents a specific invocation of a DecisionContract against specific state/evidence.

### ORDO-3-013 — DecisionOutcome
Represents the provider-neutral resolution result of a DecisionRequest.

Expected categories:
- Decided
- InsufficientEvidence
- Ambiguous
- RequiresDeliberation
- ProviderFailure

Exact F# case names may vary only if repository conventions strongly justify alternatives.

### ORDO-3-014 — DeliberationRequest
Represents an explicitly scoped open-ended reasoning request.

### ORDO-3-015 — Evidence
Represents information available to support computation, decision, verification, or transition policy.

### ORDO-3-016 — EvidenceRequirement
Represents evidence required but not necessarily available.

### ORDO-3-017 — Capability
Represents authority to request or perform an action.

### ORDO-3-018 — Obligation
Represents required unresolved work.

### ORDO-3-019 — Transition
Represents an explicit legal domain-state change.

### ORDO-3-020 — Policy
Represents deterministic interpretation of state, evidence, capability, decision, consequence, and other domain facts.

### ORDO-3-021 — Provider
Represents an implementation capable of satisfying some resolution contract.

Providers may be:
- deterministic
- human
- remote AI
- local AI
- replay
- test/fake

### ORDO-3-022 — Decision and transition shall remain distinct
A DecisionOutcome never directly means that a domain transition has occurred.

### ORDO-3-023 — Decision and outcome shall remain distinct
A decision made now and an observed real-world outcome later are different records.

### ORDO-3-024 — Confidence and calibration shall remain distinct
Provider-reported confidence is not empirical calibration.

3. AUTHORITY BOUNDARIES
======================================================================

### ORDO-3-030 — Application authority
Applications own:
- domain state
- domain transitions
- business decisions
- legal choices
- consequence definitions
- business policy
- state invariants
- domain evidence semantics

### ORDO-3-031 — Ordo authority
Executable Ordo owns reusable semantics for:
- resolution modes
- bounded decision contracts
- structured outcomes
- evidence references
- capabilities
- obligations
- escalation semantics
- provider-neutral execution boundaries
- transition precondition mechanics

### ORDO-3-032 — ROS authority
ROS owns:
- execution history
- task/run association
- provider measurement
- cost
- latency
- replay orchestration
- calibration analysis
- provider comparison
- experimentation
- optimization recommendations

ROS shall not redefine Ordo semantics.

### ORDO-3-033 — Provider authority
Providers may return information or judgments.

Providers do not own:
- domain state
- domain capability
- policy
- legal transitions
- authorization
- truth

### ORDO-3-034 — Human authority is domain-scoped
Human review does not automatically imply universal override permission.

5. V0.1 CORE SCOPE
======================================================================

### ORDO-3-050 — v0.1 shall implement ResolutionMode
Required cases:
- Compute
- Decide
- Deliberate

### ORDO-3-051 — v0.1 shall implement stable semantic identifiers
At minimum support stable identity for:
- DecisionContract
- DecisionRequest
- Evidence
- resolution execution

Use strong F# types rather than raw strings where practical.

### ORDO-3-052 — v0.1 shall implement Evidence
Evidence shall minimally support:
- stable identity
- source/provenance
- optional external reference

Do not overbuild evidence scoring in v0.1.

### ORDO-3-053 — v0.1 shall implement EvidenceRequirement
Missing required evidence must be distinguishable from a negative or uncertain decision.

### ORDO-3-054 — v0.1 shall implement DecisionContract<'T>
The contract shall include at minimum:
- stable contract ID
- semantic version
- legal typed choices
- required evidence

### ORDO-3-055 — v0.1 shall implement DecisionRequest<'T>
The request shall associate:
- contract
- relevant state snapshot or state reference
- evidence
- request identity
- state/version identity where concurrency matters

### ORDO-3-056 — v0.1 shall implement DecisionResult<'T>
At minimum:
- choice
- provider identity
- evidence references
- optional confidence

### ORDO-3-057 — v0.1 shall implement DecisionOutcome<'T>
At minimum support:
- Decided
- InsufficientEvidence
- RequiresDeliberation
- ProviderFailure

Ambiguous may be implemented in v0.1 if it remains simple; otherwise it is Class B.

### ORDO-3-058 — v0.1 shall implement confidence provenance
If confidence is present, it must identify whether it is:
- provider-reported
- derived
- empirically calibrated

v0.1 does not need to calculate calibration.

### ORDO-3-059 — v0.1 shall implement a provider-neutral decision interface
The interface must not reference concrete provider SDK types.

### ORDO-3-060 — v0.1 shall implement a deterministic fake provider
Normal unit tests shall not require paid/network AI calls.

### ORDO-3-061 — v0.1 shall implement one real provider adapter
The adapter shall remain outside Ordo.Core.

### ORDO-3-062 — v0.1 shall implement explicit transition evaluation
A decision may contribute to transition eligibility but shall not execute a transition implicitly.

### ORDO-3-063 — v0.1 shall implement typed transition failure
At minimum distinguish:
- invalid state
- missing capability
- missing evidence
- policy rejection
- stale state/version

### ORDO-3-064 — v0.1 shall implement one explicit escalation path
At minimum:
Decide → RequiresDeliberation
or:
Decide → RequiresHumanReview

### ORDO-3-065 — v0.1 shall support replay without mutation
A historical DecisionRequest may be reevaluated without executing a domain transition.

### ORDO-3-066 — v0.1 shall expose observation facts
Ordo must expose enough execution facts for ROS later to record:
- resolution ID
- contract ID/version
- provider
- decision
- confidence
- start/end timing
- escalation
- state/version identity

Ordo shall not depend on ROS.

6. V0.1 F# IMPLEMENTATION SHAPE
======================================================================

### ORDO-3-070 — F# is mandatory for first-party production code
Do not introduce C# unless an unavoidable external boundary requires it.

### ORDO-3-071 — Prefer discriminated unions for closed semantic states
Examples include ResolutionMode and DecisionOutcome<'T>.

### ORDO-3-072 — Prefer records for immutable structured data
Examples include:
- Evidence
- DecisionContract
- DecisionRequest
- DecisionResult
- ProviderIdentity

### ORDO-3-073 — Prefer pure functions in core logic
Policy and transition evaluation should generally be input → result/output with no hidden side effects.

### ORDO-3-074 — Use Result for expected failure
Expected failure is data, not an exception.

### ORDO-3-075 — Use Async/Task only at side-effect boundaries
Provider calls may be asynchronous.

### ORDO-3-076 — Use CancellationToken for provider and deliberation boundaries
Cancellation support must follow normal .NET patterns.

### ORDO-3-077 — Avoid reflection-heavy design

### ORDO-3-078 — Avoid dependency injection frameworks
Use explicit composition.

### ORDO-3-079 — Avoid framework-style service locators
Provider selection/configuration should be explicit.

21. DEFINITION OF DONE — v0.1
======================================================================

Executable Ordo v0.1 is complete only when:

1. Ordo still functions as a methodology without requiring the executable package.
2. Production executable code is F#.
3. Core has no ROS dependency.
4. Core has no concrete AI-provider dependency.
5. Compute, Decide, and Deliberate exist as explicit concepts.
6. DecisionContract<'T> exists.
7. DecisionRequest<'T> exists.
8. DecisionOutcome<'T> exists.
9. Evidence exists as a first-class concept.
10. Missing evidence is distinct from low confidence.
11. Confidence is optional.
12. Confidence provenance exists.
13. Provider-reported confidence is not labeled calibrated probability.
14. A provider-neutral interface exists.
15. A fake provider exists.
16. One real provider adapter exists.
17. Provider output is validated against legal choices.
18. Invalid provider output is rejected.
19. Decision does not execute transition directly.
20. Capability remains independent from confidence.
21. One escalation path works.
22. One stale-state decision is correctly rejected.
23. Replay works without mutation.
24. Observation facts are exposed.
25. Historical contract version is identifiable.
26. Normal tests do not require paid/network AI.
27. Existing tests still pass.
28. Build remains clean.
29. Documentation contains at least one complete example.
30. Documentation contains explicit anti-patterns.
31. No workflow engine was introduced.
32. No rules engine was introduced.
33. No agent framework was introduced.
34. No unrelated refactoring was performed.
35. Another engineer or agent can understand the v0.1 execution model without hidden conversational context.

24. GOVERNING PRINCIPLE
======================================================================

The implementation shall preserve this authority chain:

Domain State
    ↓
Domain Contract
    ↓
Resolution Requirement
    ↓
Compute / Decide / Deliberate
    ↓
Structured Result
    ↓
Evidence + Capability + Policy + State-Version Check
    ↓
Legal Transition
    ↓
New Domain State

The intelligence provider does not appear in the authority chain as an owner.

It supplies information.
It may contribute judgment.
It may identify uncertainty.
It may request escalation.

It does not own:
- truth
- state
- authority
- capability
- policy
- transition legality

======================================================================
25. FINAL PASS 3 CONSTRAINT
======================================================================

When implementation convenience conflicts with semantic explicitness, semantic explicitness wins.

The system must not hide:
- uncertainty
- missing evidence
- authority
- state version
- contract version
- provider identity
- policy identity where relevant
- failure
- escalation
- side effects
- causality

The goal of executable Ordo is not to make complexity disappear.

The goal is to make important complexity explicit, typed, testable, observable, and difficult to misuse.
